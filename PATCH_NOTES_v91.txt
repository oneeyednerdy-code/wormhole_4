WORMHOLE ALPHA-0.0.91 PATCH NOTES
Road to D1: API Gateway

Alpha-0.0.91 begins the backend boundary needed before Wormhole adopts Cloudflare D1 in 0.1.0.
No D1 database is created or used in this release.

ADDED
- Added a same-origin Cloudflare Worker gateway for Twitch Helix API requests.
- Added an allowlist of Twitch endpoints Wormhole is permitted to proxy.
- Added Worker-side validation for Twitch authorization and Client ID headers.
- Added normalized JSON errors for unsupported routes, missing authorization, and temporary upstream failures.
- Preserved Twitch rate-limit response headers so future Wormhole releases can make smarter request decisions.
- Added TWITCH_CLIENT_ID to Wrangler environment variables for the Worker gateway.

CHANGED
- Browser Twitch API calls now go to /api/twitch/helix/* on Wormhole instead of calling api.twitch.tv directly.
- The Cloudflare Worker forwards approved requests to Twitch Helix.
- TwitchTracker continues to use the existing server-side /api/twitchtracker-summary route.
- OAuth authorization, token validation, and token revocation remain with Twitch in this release. Moving OAuth/session ownership server-side is intentionally reserved for a later pre-D1 patch.
- Advanced Wormhole source/cache/release identifiers to Alpha-0.0.91.

SECURITY / ARCHITECTURE
- The gateway does not store Twitch access tokens.
- Twitch bearer tokens are forwarded only to Twitch's Helix API for the current request.
- Arbitrary upstream URLs cannot be supplied through the gateway.
- Only explicitly supported Helix paths are accepted.
- D1 is not required and no persistent server-side creator database has been introduced.

WHY THIS MATTERS FOR 0.1.0
The browser now talks to Wormhole for Twitch data instead of being tightly coupled to Twitch Helix. This gives future releases one backend layer where caching, rate-limit handling, normalized creator data, server-side sessions, and eventually D1 repositories can be added without rewriting the UI.

DEPLOYMENT
